- Changed:
  - `app/src/parse/` (new) is a line-for-line port of `ingest/parse/parser.py`, `units.py` and
    `ingest/taxonomy/normalize.py`. It gives the same output shape: `{qty, qty_max, unit, slug,
    raw_name, prep, optional, note, pkg}`.
    - `py.ts` gives the port Python's semantics. It compiles patterns written in Python syntax
      with Unicode `\w \s \d \b`. It also has `str.strip/split`, `int()` for Unicode digits, and
      a `round(x, 4)` that rounds ties to even.
    - The word tables (`tables.gen.json`) are exported verbatim from Python. The regexes and
      control flow are ported by hand.
    - The synonym index is built from `slugs.json`. It needed one more field, `explicitMeat`,
      for the "veggie X" rule, so `gen_slugs.py` now writes it. slugs.json is otherwise
      identical to a fresh regeneration.
  - Parity is enforced by `app/src/parse/parity.test.ts`. The test reads
    `ingest/parse/gold.jsonl` and `ingest/fixtures/ingredient_lines_sample.txt` directly and
    compares every item with `testdata/python_parse.json`. That snapshot is the Python output,
    written by `app/scripts/gen_parse_snapshot.py`, which also writes the tables. The snapshot
    stores its input lines, so if it goes stale against `ingest/` the test fails instead of
    comparing the wrong lines. The test also fails on any difference not listed in
    `KNOWN_DIFFERENCES` (currently empty), and on a listed difference that no longer occurs.
  - user.db migration v5 adds two columns:
    - `my_recipes.parsed`: JSON with one `{raw, items:[{slug, qty, qtyMax, unit, pkgQty,
      pkgUnit, optional}]}` per line.
    - `my_recipes.parser_version`.

    Create, update and fork write both. On read, the stored parse is used only if its version
    and its raw lines match the recipe. Otherwise the lines are parsed again, and those lines
    are counted in `parseStats.reparsed` (rule 11). This covers pre-v5 rows and old backups.
  - My Recipes lines are now raw text (`MyRecipeIngredientLine.raw`; `features/myRecipes/lines.ts`).
    The editor has one text field per ingredient. Under each line it shows what was understood
    ("2 cups → cilantro"), shows "Heading: not an ingredient", or marks the line in the accent
    colour as "Not understood: this line stays as typed and goes to "Check these"".
    - The quantity, unit and name fields are still derived from the parse, so the fork diff
      keeps working. The name is kept while the line still resolves to the same slug, so
      "4 tbsp vegetable oil" reads as Changed, not as a remove plus an add.
    - A fork copies each parent line as text ("2 tbsp vegetable oil").
    - A saved recipe now has "Add to plan".
  - In `features/plan/recipeLookup.ts`, a 'my' entry now gives one PlanLine per parsed item,
    with slug, qty, qtyMax, unit and pkg. These lines are scaled and aggregated like corpus
    lines. Only items with no slug go to "Check these". Headers give no line, as in the corpus
    build.

- Design was wrong about:
  - The brief says the editor lines are "raw text on the phone". Before this slice they were
    three structured fields (qty, unit, name). I replaced those with one text line. The
    structured fields are still stored, derived from the parse, because the fork diff and old
    rows use them.
  - "Matching" in the cook engine is SQL over corpus.db only, so My Recipes are not
    candidates there. This slice stores the slugs that matching would need, and uses them for
    the kitchen-list "have" check in the grocery build. Wiring My Recipes into "What can I cook"
    is not done; see Open.
- Open:
  - Should My Recipes appear in "What can I cook?" results? My recommendation: yes, as a
    follow-up slice. Their stored slugs make it a JS-side union with the SQL candidates.
  - Note for whoever regenerates `slugs.json` or changes the parser: bump `PARSER_VERSION` in
    `src/parse/index.ts`, and re-run `python3 scripts/gen_parse_snapshot.py`. The version bump
    is what makes stored parses re-read.
