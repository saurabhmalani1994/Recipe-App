- Changed:
  - `app/src/features/importUrl/` (new): "Import from link" (D6, no AI).
    - `jsonld.ts` parses schema.org `Recipe` JSON-LD: walks `@graph` and plain arrays at any
      depth to find a `Recipe` node (BBC Good Food and blogspot both sometimes bury it there),
      reads title/yield/times (`duration.ts` parses `PT1H30M`)/ingredients/image/cuisine/category,
      and flattens `recipeInstructions` (`HowToStep`, and `HowToSection` with its name kept as
      its own step so the grouping survives).
    - `microdata.ts` is the fallback once no `<script>` gives a usable `Recipe`: the same fields
      read from `itemscope`/`itemtype`/`itemprop`, including nested `HowToStep`/`HowToSection`
      scopes.
    - `textFallback.ts` heuristically splits plain pasted text with no structured data: explicit
      "Ingredients"/"Instructions" headings when present, else a per-line shape classifier
      (quantity-led vs. a verb-led or numbered sentence).
    - `parseImportInput.ts` orchestrates all three (HTML vs. plain text is told apart by whether
      the pasted content starts with a tag), plus a last-resort pass that runs the plain-text
      heuristic over an HTML page's own visible text when neither JSON-LD nor microdata gave
      anything.
    - `fetchRecipePage.ts`: `CapacitorHttp.get` on native (no CORS); a plain `fetch` in the
      browser build, which the screen explains usually fails on CORS.
    - `toMyRecipeData.ts`/`cuisineMatch.ts` map the parsed result to a `MyRecipeData`: each
      ingredient keeps only its raw text (`raw`) — S13's parser reads it exactly like a
      hand-typed line, once the editor renders it. `cuisine` is matched against `Cuisine` by
      substring/alias, never guessed.
  - `app/src/routes/ImportFromUrl.tsx` (new, `/my-recipes/import`, linked from My Recipes): a URL
    field + fetch button, a paste box always offered alongside (with the CORS explanation on
    web), and a parsed preview (title, ingredient/step counts and lists) before handing off to
    the editor via router state.
  - `MyRecipeData` gained `sourceUrl` (`features/myRecipes/types.ts`) — no db migration, it is
    part of the existing JSON `data` blob. The editor shows "Imported from: <url>" when set.
  - My Recipes in Cook results (owner: "Upload my own recipes ... to copy an existing version
    and make a version of it"):
    - `features/cook/taxonomy.ts` now loads `ingredients.flags` (was unread) into
      `Taxonomy.flags`.
    - `features/myRecipes/myRecipeDiet.ts` computes a My Recipe's diet status for the active
      preset from those flags (R7 vegetarian = `explicit_meat`, R8 no red meat = `red_meat`) and
      the engine's own `fittingSwaps`/`loadSwapTable` — not a port of `ingest/tag/diet.py`'s full
      word-list/steps-scan, just what the brief asked for.
    - `features/myRecipes/myRecipeMatch.ts` is the JS-side union: builds the same
      core/covered/missing/substitutable shape `matchRecipes` computes from SQL, from each My
      Recipe's stored parse (S13) instead, applies cuisine + diet, and marks results `mine`.
      `engine.ts` now exports `compareResults` (the ranking `matchRecipes` already used) and
      `DEFAULT_MATCH_LIMIT`, so both are re-sorted and capped the same way.
    - `routes/Cook.tsx` merges `matchMyRecipes` in beside `matchRecipes`, sorts the union, and
      routes a "Mine" result to the My Recipe editor (`recipeSource: 'my'` on "Add to plan")
      instead of the corpus recipe detail screen.

- Design was wrong about:
  - S13's report flagged this as open ("Should My Recipes appear in 'What can I cook?'
    results? ... a JS-side union with the SQL candidates"). This slice does that.
  - The brief's diet line ("Diet status is computed from the taxonomy flags ... including
    adaptable where a substitution exists; reuse the engine's swap logic") is narrower than
    `ingest/tag/diet.py`, which the corpus build actually runs: the tagger also reads raw text
    for an unresolved item's meat words, alternatives written in a line's note ("or vegetable
    broth"), and meat the steps mention but the ingredient list doesn't. A My Recipe's diet
    status here only looks at the taxonomy flag on each parsed item's own slug (unresolved items
    are skipped, never a blocker) — matches the brief as given, but is not the same computation
    the corpus recipes get tagged with, so "adaptable"/"no" can read differently for a
    superficially similar ingredient list. Noted in `myRecipeDiet.ts`'s own comment too.
- Open:
  - `matchMyRecipes` applies only `have` (with substitution), `cuisine` and `diet` — "one pot",
    "use only equipment" and "under N minutes" pass every My Recipe through unfiltered, since
    `MyRecipeData` carries no course, equipment or timing at all. My recommendation: if a My
    Recipe should answer those filters too, the fields need to exist on `MyRecipeData` first
    (a separate slice — the owner would need to say whether that data entry belongs in the
    editor, is inferred from steps/ingredients, or is simply left unfilterable by design).
  - A My Recipe result's `quality` is fixed at 0 (there's no corpus-style quality score for it),
    so on a tied coverage band it always sorts after a corpus recipe with the same covered count.
    Fine for the brief's two tests; worth an owner call if "Mine" recipes should get a rank
    boost instead.
  - The cuisine mapping (`cuisineMatch.ts`) is a small substring/alias table over `Cuisine`'s ~26
    values, not exhaustive of everything schema.org sites write in `recipeCuisine`; an
    unrecognised value is silently dropped (cuisine stays null) rather than guessed, so the
    owner may need to set it by hand sometimes.
